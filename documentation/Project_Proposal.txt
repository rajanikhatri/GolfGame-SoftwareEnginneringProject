While many online games exist, not all classic memory-based card games are available in a structured multiplayer web format.For this project, our team proposes to build a web-based multiplayer version of the card game ÒGolf.Ó This game is both memory-based and strategy-driven. Players must remember hidden card values, make quick decisions, and manage risk throughout the round. Implementing this game digitally introduces interesting software engineering challenges, including real-time multiplayer synchronization, consistent rule enforcement, session management, and persistent data storage.From a software engineering perspective, this project allows us to explore requirements analysis, system design, task allocation, implementation, testing, and presentation. This card game requires thoughtful architecture and coordination across multiple components.2 ProposalOur goal is to design and implement a fully functional web-based multiplayer version of Golf that supports up to six players in a single session.The system will include:==> User authentication (account creation and login)==> Game room creation with a unique join code==> Multiplayer synchronization==> Game logic engine==> Leaderboard tracking cumulative performanceOne player will create a game room, and the system will generate a room code. Other players can join using this code. This structure allows players to connect remotely in a controlled session.We will divide the project into structured components such as requirements documentation, system design, frontend implementation, backend implementation, testing, and deployment.2.1 System Description and Game RulesEach player is dealt four cards. At the beginning of each round, players have five seconds to look at two of their four cards and memorize them. After that, cards remain hidden unless revealed through game mechanics.The objective of the game is to achieve the lowest cumulative score possible. Negative values are beneficial.Power CardsPower cards can only be activated if they are drawn directly from the deck during a playerÕs turn. If a power card is already in a playerÕs hand, it does not automatically activate.When a player draws a power card, they may either:==> Use the special ability of the card, or==> Ignore the power and swap the drawn card with one of their four existing cards.Power card behaviors:==> 7: Peek at one of your own cards.==> 8: Peek at one opponentÕs card.==> 9: Peek at any two cards in the game and optionally swap them.==> 10: Blindly swap two playersÕ cards without viewing them first.After using (or skipping) the power, the player may still decide whether to keep the drawn card or replace one of their four cards.Special Scoring Cards==> Black King: -2 points==> Joker: -1 pointThese cards reduce the total cumulative score.Matching Rule (Reaction Mechanism)If a player discards a card (for example, a 7), other players have three seconds to discard the same card if they believe they have it.If multiple players react within the three-second window, the system determines who acted first. The fastest player successfully discards their card.If another player reacts slightly later but still within the time window, they must take their card back and draw one additional penalty card.If a player discards the wrong card (for example, throws an 8 instead of a 7), they must take the card back and draw one penalty card.If a player attempts to react after the three-second window has passed, the matching option will already be disabled by the system. In that case, the player cannot discard and receives no penalty.Knock MechanismThe game does not have a fixed time limit. Instead, if a player believes they have the lowest score, they may ÒknockÓ by clicking the knock button.Once a player knocks, the game continues for one final round until it returns to that player. All cards are then revealed and final scores are calculated.If the player who knocked does not have the lowest score at the end, 50 penalty points are added to their cumulative score.2.2 Deliverables==> Software Requirements Document (or structured user stories)==> System Design Documentation (including UML diagrams)==> Project Schedule with role allocation==> Frontend implementation (React interface)==> Backend implementation (Node.js (JavaScript) game logic and server)==> Multiplayer session management module==> Database integration for authentication and leaderboard==> Testing Plan and Test Cases==> Final working application==> Class presentation and demonstration2.3 TasksMajor tasks include:1.
